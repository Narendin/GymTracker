# GymTracker: правила для агентов

Прочитай это до первой команды. Документация — единственный источник
правды; здесь только указатели, детали не дублируются.

Команды сборки, установка на эмулятор/телефон и известные ловушки —

## Документация

- `docs/STATE.md` — состояние приложения: экраны (коды A1, B1, B2…),
  переходы, состояния. Правки сверяют с ним и обновляют его.
- `docs/gym-tracker-requirements.md` — спецификация.
- `docs/CHANGELOG.md` — описания изменений; секция `[Unreleased]` для
  незакоммиченного, релизные секции — по датам.
- `docs/BUILD.md`, `docs/RELEASE.md` — сборка и выпуск.

## Скиллы

В проекте три скилла:

- `skills/git-workflow/SKILL.md` — порядок issue → ветка → проверки перед
  коммитом → коммит → PR → мерж → уборка. Использовать на любую операцию с
  git (issue, коммит, push, PR, мерж, удаление ветки, релиз).
- `skills/run-autotests/SKILL.md` — прогон инструментальных автотестов:
  перезапуск эмулятора, очистка данных, фоновый прогон с опросом, чтение
  XML-отчёта, проверка на чистом эмуляторе. Использовать перед любым коммитом,
  который трогает код приложения, и на любую просьбу прогнать автотесты.
- `skills/write-autotests/SKILL.md` — написание и расширение автотестов
  (`AppFlowTest`): структура, конвенции, testTag, вспомогательные функции,
  добавление методов. Использовать при новом функционале, исправлении бага
  или изменении поведения, требующем покрытия автотестом.

Скиллы среды агента обязательны, если среда их даёт:

- `code-review` — обязательно перед коммитом и перед созданием PR: проверка
  диффа сначала на правильность, находки с номерами строк;
- `commit-messages` — обязательно при написании сообщения коммита.

## Правила проекта

- Общение с пользователем — на русском языке.
- Интерфейс только на русском; вес только в кг; приложение офлайн.
- Навигация — собственный стек в `ui/GymApp.kt`, новых экранов не
  добавлять без правки `docs/STATE.md`.
- Бинарники (`build/`, APK, AAB) в репозиторий не коммитятся.
- `secrets.properties` и `local.properties` в `.gitignore`, в публичные
  файлы не попадают.
- **Значения из `secrets.properties` не публикуются никогда.** Это
  `applicationId`, путь к ключу, alias и пароли: не попадают в код,
  документацию, комментарии, тексты issue, PR и релизов. В файлах
  репозитория пишутся `<applicationId>`, `<путь к ключу>`, `<alias>`;
  отпечатки ключей в документации не пишутся. Перед коммитом проверка:
  `git grep -I -n <значение из secrets.properties>` — 0 совпадений.
- Коммит-сообщения — на английском. Тексты issue, PR и релизов — на русском.
- **В коде не должно быть ссылок на документацию, issue, PR и релизы.**
  Комментарий объясняет суть по месту, без `issue #N`, `docs/...` и номеров
  релизов: ссылка указывает на источник, который меняется, комментарий
  обязан оставаться верным. Ссылки живут в документации, commit-сообщениях,
  issue и PR. Чек-лист и проверка — `skills/git-workflow/SKILL.md`.
- Документация по задаче — в PR этой задачи: правятся все файлы
  документации, описывающие то, что задача меняет. Список файлов и что в
  них — раздел «Документация» этого файла; новые файлы документации
  добавляй в тот список, и они тоже под правилом. PR без своей
  документации не мержат.
- В описании PR — первой строкой технический маркер `Closes #N` (GitHub
  связывает issue и закрывает её при мерже только по английскому ключевому
  слову), остальной текст на русском.
- **Коммит и создание PR — только по явному указанию пользователя.** Не
  «по завершении вехи», не из вежести: подготовь сообщение и спроси.
- Работу по issue ведут в отдельной ветке, в `Master` напрямую не коммитят;
  изменения попадают в `Master` через PR.
- PR без issue не создаются: сначала заводится issue и она описывает, что
  и зачем делается; PR ссылается на неё первой строкой (`Closes #N` или
  `Refs #N`).
- Юнит-тесты (`:app:test`) в изолированной среде могут падать на
  `GradleWorkerMain` — это среда, не код; компиляция (`:app:assembleDebug`)
  это проверка кода.
- **Каждый исправленный баг и каждый новый/изменённый функционал покрывается
  тестами.** Исправление бага — автотест, воспроизводящий сценарий и
  проверяющий корректное поведение. Новый или изменённый функционал —
  автотест по сценарию пользователя. Чистые функции (форматы, плюрализация)
  — юнит-тест. PR без нового теста на изменение кода приложения не мержат.
