# GymTracker: правила для агентов

Прочитай это до первой команды. Документация — единственный источник
правды; здесь только указатели, детали не дублируются.

## Перед сборкой

Рабочий JDK на этом компьютере — `C:\Users\Владимир\.jdks\jbr-21.0.11`.
Java 25 (её ставит Android Studio) Gradle 8.7 не понимает, сборка падает.
Задай его перед любой командой Gradle:

```
$env:JAVA_HOME='C:\Users\Владимир\.jdks\jbr-21.0.11'
```

Команды сборки, установка на эмулятор/телефон и известные ловушки —
`docs/BUILD.md`. Порядок релиза, тег и GitHub Release — `docs/RELEASE.md`.

## Документация

- `docs/STATE.md` — состояние приложения: экраны (коды A1, B1, B2…),
  переходы, состояния. Правки сверяют с ним и обновляют его.
- `docs/gym-tracker-requirements.md` — спецификация.
- `docs/CHANGELOG.md` — описания изменений; секция `[Unreleased]` для
  незакоммиченного, релизные секции — по датам.
- `docs/BUILD.md`, `docs/RELEASE.md` — сборка и выпуск.

## Скиллы

В проекте один скилл — `skills/git-workflow/SKILL.md`: порядок issue →
ветка → проверки перед коммитом → коммит → PR → мерж → уборка. Использовать
его на любую операцию с git (issue, коммит, push, PR, мерж, удаление ветки,
релиз).

## Правила проекта

- Интерфейс только на русском; вес только в кг; приложение офлайн.
- Навигация — собственный стек в `ui/GymApp.kt`, новых экранов не
  добавлять без правки `docs/STATE.md`.
- Бинарники (`build/`, APK, AAB) в репозиторий не коммитятся.
- `secrets.properties` и `local.properties` в `.gitignore`, в публичные
  файлы не попадают.
- Коммит-сообщения — на английском. Тексты issue, PR и релизов — на русском.
- Документация по задаче — в PR этой задачи: правятся все файлы
  документации, описывающие то, что задача меняет. Список файлов и что в
  них — раздел «Документация» этого файла; новые файлы документации
  добавляй в тот список, и они тоже под правилом. PR без своей
  документации не мержат.
- В описании PR — первой строкой технический маркер `Closes #N` (GitHub
  связывает issue и закрывает её при мерже только по английскому ключевому
  слову), остальной текст на русском.
- Работу по issue ведут в отдельной ветке, в `Master` напрямую не коммитят;
  изменения попадают в `Master` через PR.
- PR без issue не создаются: сначала заводится issue и она описывает, что
  и зачем делается; PR ссылается на неё первой строкой (`Closes #N` или
  `Refs #N`).
- Юнит-тесты (`:app:test`) в изолированной среде могут падать на
  `GradleWorkerMain` — это среда, не код; компиляция (`:app:assembleDebug`)
  это проверка кода.
