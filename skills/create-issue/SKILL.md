# Создание issue GymTracker

Issue описывает задачу: что и зачем делается. PR без issue не создаются.
Репозиторий `github.com/Narendin/GymTracker`, базовая ветка `Master`.
Порядок git целиком — `skills/git-workflow/SKILL.md`; здесь только заведения issue.

## Железные правила

1. **Название и тело issue — по-русски.** Коммит-сообщения — английский.
2. **Одна issue = одна тема.** Разные темы не сваливать в одну issue;
   зависимости указывать строкой «Зависит от issue #N».
3. **Тело issue — из файла, прочитанного в UTF-8.** PowerShell 5.1 читает
   файлы по умолчанию в CP1251, и `Get-Content -Raw` без `-Encoding utf8`
   превращает кириллицу в искажение кодировки (проверено: три issue ушли в
   GitHub искажённой кодировкой). Проверка после отправки обязательна.
4. **Секретов в тексте нет.** `applicationId`, путь к ключу, alias, пароли и
   отпечатки ключей не пишутся; в тексте — `<applicationId>`, `<путь к ключу>`,
   `<alias>`. Реальный репозиторий в URL текста issue не подставлять, писать
   `владелец/репозиторий`.
5. **Создание issue — по явному указанию пользователя.** Подготовь текст и спроси.

## Шаг 1. Проверка существующих

- `& "C:\Program Files\GitHub CLI\gh.exe" auth status` — аккаунт `Narendin`,
  токен с правом `repo`.
- `& "C:\Program Files\GitHub CLI\gh.exe" issue list --state all --limit 40` —
  список всех issue. Дубликат не заводить: существующую issue дополняют
  комментарием, новую не создают.

## Шаг 2. Текст

Структура тела, по-русски:

```
одна строка: что это и где сейчас (серая строка D1, незакрытый экран, баг)

**Что делаем**
конкретные действия и поведение

**Зачем**
проблема пользователя

**Технически**
решение, разрешения, формат, ограничения

**Открытые вопросы**
что решить до реализации

**Проверка**
- юнит-тест: что проверяет
- автотест: сценарий пользователя
- ручная проверка: на телефоне/эмуляторе
- Документация: файлы, которые правит PR
```

- Раздел «Проверка» обязателен: каждый исправленный баг и каждый новый или
  изменённый функционал покрывается тестами. Чистые функции — юнит-тест,
  сценарий пользователя — автотест.
- Раздел «Документация» перечисляет файлы, описывающие то, что задача меняет:
  `docs/STATE.md`, `docs/gym-tracker-requirements.md`, `docs/CHANGELOG.md`,
  при необходимости `docs/BUILD.md`, `docs/RELEASE.md`. PR без своей
  документации не мержат.
- Ссылки на документацию и другие issue в теле issue — можно. В коде
  ссылок быть не должно.
- Тесты и документация в issue описываются по сценарию, без готового кода.

## Шаг 3. Отправка

- Тело писать во временный файл `issue-<тема>-body.md` в корне проекта. Файл
  в коммит не идёт и удаляется после отправки.
- Отправка:

```
$body = Get-Content -Raw -Encoding utf8 "F:\Pets\GymTracker\issue-<тема>-body.md"
& "C:\Program Files\GitHub CLI\gh.exe" issue create -t "<Название по-русски>" -b $body
```

- Заголовок, переданный строкой в командной строке, кодировку не теряет;
  тело из файла — всегда с `-Encoding utf8`.
- Записать номер issue: он нужен первой строкой описания PR (`Closes #N`).

## Шаг 4. Проверка после отправки

```
$json = & "C:\Program Files\GitHub CLI\gh.exe" issue view <N> --json title,body | ConvertFrom-Json
($json.body -split "`n")[0]
($json.body | Select-String -Pattern 'Р­|РСЏ|СЏ|Рђ' -AllMatches).Matches.Count
```

- Первая строка читается по-русски, совпадений искажённой кодировки — 0.
- Если кодировка искажена: `gh issue edit <N> -b (Get-Content -Raw -Encoding utf8 <файл>)`
  и повторить проверку. Заголовок править `gh issue edit <N> -t "<новый>"`.

## Шаг 5. Уборка

- `Remove-Item <файл тела>`.
- `git status --short` — чисто: временные файлы текста в коммит не попадают.
- Ссылки на issue дать пользователю: `github.com/Narendin/GymTracker/issues/<N>`.
